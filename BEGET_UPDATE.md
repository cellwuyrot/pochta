# Кабинет проекта и несколько почтовых ящиков Beget — версия 2.1.0

Обновление подготовлено по исходному архиву smtp.zip. Это обновление файлов кода, не подключение к вашему серверу или GitHub. Если после исходного архива вы меняли Python-код/шаблоны, сначала сравните изменения с `reports/beget-changes.diff` и своей версией. Обновление заменяет перечисленные в манифесте файлы.

## Что добавлено

- **Сайты → Кабинет / Почты**: отдельный кабинет каждого проекта.
- Несколько зарегистрированных почтовых ящиков на один проект, каждый со своим адресом, именем и SMTP-паролем.
- Добавление, редактирование, отключение, удаление подключения и выбор адреса по умолчанию.
- Проверка SSL/TLS-подключения и SMTP-авторизации. Эта проверка не отправляет письмо и не гарантирует доставку.
- Форма отправки с выбором активного адреса; письмо сохраняется в существующую долговечную очередь.
- Правильный выбор аккаунта по `from_email` при отправке через API, шаблоны и SMTP.
- Ящики Beget используют smtp.beget.com:465, SSL/TLS, логин — полный email. Данные пароля относятся к ящику, не к панели Beget.
- Пароли шифруются существующим SecretText/Fernet; не возвращаются в API/HTML. SMTP-ошибки очищаются от пароля и AUTH-кодировок перед логированием.
- Изоляция по проекту: API-ключ одного сайта не использует ящики другого.
- Обновлены DNS-подсказки: при использовании ящиков Beget сервис не предлагает заменить MX/DKIM на свои.
- Исправлено принятие SMTP_HOST_PORT из .env.

## Границы этой версии

Ящики создаются в Beget вручную, а здесь подключаются уже существующие. Создание/удаление ящиков через Beget API не реализовано. Удаление подключения НЕ удаляет ящик в Beget.

**IMAP-синхронизации и интерфейса чтения входящих писем в этом обновлении нет.** Входящие остаются в Beget; в кабинете есть ссылка на web.beget.email. Сервис не становится полноценным веб-почтовым клиентом. Копирование исходящих в папку «Отправленные» через IMAP тоже не реализовано.

Кабинеты доступны существующим администраторам сервиса. Отдельные учётные записи владельцев проектов с разграничением прав кабинета не добавлены; API-ключи проектов изолированы.

## Как обновить сервер

Предполагается, что проект расположен в /root/pochta и называется smtp-service в Docker Compose. Архив обновления не содержит .env, tls/, data/, Dockerfile или docker-compose.yml и не заменяет ваши сертификаты, Compose-порты или proxy-настройки.

1. Сохраните архив `smtp-beget-update.zip` на сервере как `/root/smtp-beget-update.zip`.
2. Если команда `unzip` отсутствует, установите её для своей ОС.
3. Выполните команды ниже. При ошибке резервного копирования НЕ продолжайте распаковку.

```bash
set -e
cd /root/pochta
unzip -p /root/smtp-beget-update.zip tools/backup_before_beget.sh > /root/backup_before_beget.sh
bash /root/backup_before_beget.sh /root/pochta
unzip -o /root/smtp-beget-update.zip -d /root/pochta
docker compose up -d --build --force-recreate smtp-service
sleep 10
docker compose ps
docker compose logs --since=2m --tail=80 smtp-service
curl -f https://smtp.trioz.ru/api/health
```

Скрипт создаёт закрытую папку `/root/pochta-backups/beget-<дата>-<суффикс>`:

- `project-before.tar.gz`: исходные файлы, .env и TLS-файлы, если они находятся в каталоге проекта;
- `data/`: остановленный снимок тома /app/data, включая SQLite, `.encryption_key` и `.secret_key`.

Резервная копия содержит секреты. Не загружайте её в GitHub и не отправляйте публично. При использовании внешних путей сертификатов/ключей или других томов сохраните их отдельно. Не используйте `docker compose down -v` и не удаляйте smtp-data.

После резервного копирования сервис остаётся остановленным до команды запуска. Если отменили обновление и код не меняли, выполните `docker compose up -d smtp-service`.

При первом запуске SQLAlchemy создаёт таблицу mailboxes, миграция добавляет sites.mailbox_mode и фиксирует версию схемы 2. Имеющиеся сайты, пользователи, API-ключи, шаблоны и очередь сохраняются. Не удаляйте существующий ключ шифрования: он нужен и для старых, и для новых секретов.

На случай отката сохраните точный путь копии: остановите сервис, восстановите согласованный исходный код и содержимое тома /app/data вместе с ключами из этой копии, затем пересоберите образ. Если после обновления уже были новые письма/ящики, откат снимка потеряет эти новые данные — сначала сделайте дополнительную копию.

## Как пользоваться

1. Откройте https://smtp.trioz.ru/admin/sites.
2. Создайте/выберите проекты `trioz.ru` и `buisness.trioz.ru` как две отдельные записи. Написание buisness сохранено как в запросе.
3. Нажмите «Кабинет / Почты» у нужного проекта.
4. «Добавить почту»: полный адрес уже созданного в Beget ящика, имя и пароль ящика.
5. Нажмите «Проверить». При 535 проверьте пароль именно ящика и доступность аккаунта в Beget.
6. Повторите для всех ящиков; выберите адрес по умолчанию.
7. В форме отправки выберите «От кого» и отправьте новое тестовое письмо на свой внешний адрес. Посмотрите историю попыток и папки получателя.

Пример структуры (адреса условные, не создаются автоматически):

```text
Проект trioz.ru
  info@trioz.ru
  sales@trioz.ru

Проект buisness.trioz.ru
  business@trioz.ru
  support@buisness.trioz.ru
```

Домен проекта может отличаться от домена подключённого ящика. Адрес должен реально существовать в Beget. Один и тот же ящик можно вручную подключить к нескольким проектам, но каждого проектного API-ключа хватает только на его собственное подключение.

Первый активный ящик становится отправителем по умолчанию. Отключение/удаление адреса по умолчанию выбирает следующий активный ящик. Если активных адресов нет, отправка блокируется. После подключения первого ящика включается mailbox_mode: провайдеры/legacy relay и Direct MX больше не используются для этого проекта, даже если все ящики удалены. Неудача одного аккаунта не приводит к отправке под другим аккаунтом.

SMTP-сервер Beget должен быть доступен с VPS на исходящем TCP-порту 465. Учитывайте лимиты и правила Beget; это не система обхода лимитов или сервис массовых рассылок. Accepted означает принятие сервером, не попадание в почтовый ящик.

## Входящая почта и DNS

**MX доменов почтовых ящиков должны остаться на Beget.** Если раньше вы заменили их на smtp.trioz.ru по инструкции самостоятельного входящего SMTP, восстановите MX по актуальным настройкам панели Beget. Не угадывайте значения MX и не смешивайте два разных почтовых хостинга.

A-запись smtp.trioz.ru по-прежнему указывает на VPS для HTTPS-панели и SMTP-приёма от ваших приложений. SPF/DKIM/DMARC настраиваются по инструкции Beget для домена email, который может отличаться от домена сайта. Не создавайте две SPF-записи. Проектная DKIM-подпись при маршруте через зарегистрированный ящик не добавляется: подпись/доменная настройка обслуживаются Beget.

## API: несколько адресов

- `GET /api/mailboxes`: список активных адресов своего проекта и адрес по умолчанию. Паролей в ответе нет.
- `POST /api/outbox`: сохраняет задание и возвращает 202/queued. Выбор адреса — `from_email`.
- `GET /api/outbox/{id}`: состояние задания своего проекта.
- `POST /api/emails`: существующий синхронный API, теперь тоже использует аккаунт выбранного адреса.
- `POST /api/send`: для шаблонов добавлено необязательное `from_email`. Без него используется адрес по умолчанию.

Для глобального ключа укажите проект через `?site_domain=buisness.trioz.ru`. В синхронном `/api/emails` неоднозначный общий ящик требует явного site_domain. Предпочитайте API-ключ конкретного проекта.

Тело запроса в /api/outbox, с API-ключом выбранного проекта в Authorization: Bearer:

```json
{
  "from_email": "sales@trioz.ru",
  "to": "your-test-address@gmail.com",
  "subject": "Проверка Beget",
  "text": "Письмо через выбранный почтовый ящик"
}
```

SMTP-клиенты по-прежнему авторизуются учётной записью пользователя ЭТОГО сервиса через STARTTLS, а не паролем Beget. В разрешениях smtp_domains такого пользователя указываются домены проектов. Заголовок From и envelope sender должны совпадать с зарегистрированным ящиком. Если одинаковый sender подходит нескольким разрешённым проектам, SMTP отвергает неоднозначность — используйте проектный API-ключ или ограничьте пользователя одним проектом.

## Безопасность и старые очереди

- Ключ Fernet живёт вне SQLite в /app/data/.encryption_key либо задаётся DATA_ENCRYPTION_KEYS. Защищайте и резервируйте его вместе с БД.
- Пароли меняйте через HTTPS-кабинет; не записывайте их в репозиторий/логи и не присылайте в чат.
- Старая очередь при обработке заново проверяет активность сайта и точный зарегистрированный адрес. Старое письмо от неподключённого адреса завершится failed, а не отправится через чужой ящик.
- unknown/uncertain автоматически не повторяется. В случае старых 550-писем сначала проверьте историю; после исправления маршрута отправьте новое тестовое сообщение.
- При изменении пароля в Beget обновите его в кабинете проекта.

## Проверки и ограничения тестирования

В локальной среде: 231 тест прошёл, включая 26 новых проверок почтовых ящиков; Ruff без ошибок; синтаксис скрипта резервирования проверен. Проверены маршрутизация двух ящиков, межпроектная изоляция, миграция, сохранение секретов, отсутствие fallback, очередь, CSRF/Origin, SMTP From, очистка ошибок и шаблонные отправки.

Интерфейс проверен на desktop 1440px и mobile 390px, включая пустой кабинет, ошибки, редактирование, DNS и меню. Локальные интерактивные сценарии создают только тестовые аккаунты и очередь, без внешней отправки.

Реальная авторизация в вашем Beget, отправка в Gmail и сборка Docker на вашем VPS НЕ выполнялись: у нас нет доступа к вашему серверу и почтовым учётным данным. В среде подготовки нет Docker CLI, поэтому резервный скрипт проверен синтаксически, но не запускался с реальным Docker-томом. После установки обязательна проверка «Проверить» и одно новое тестовое письмо.
