# Обновление и эксплуатационные ограничения

Это доработка существующего FastAPI/Jinja-проекта, не новый сервис. Production-деплой не выполнялся.

## Перед обновлением

1. Остановите старый экземпляр, сохраните SQLite через `python tools/backup.py backup data/smtp.db backups/smtp.db`.
2. Отдельно сохраните `.env`, `data/.secret_key`, `data/.encryption_key`, TLS cert/key. Бэкап SQLite **не заменяет** бэкап ключа шифрования. Держите ключ отдельно от БД/архива и ограничьте доступ.
3. Установите зависимости: `python -m pip install -e '.[dev]'`. Для запуска пакета нужны SQLAlchemy asyncio и greenlet; зависимость исправлена.
4. Поддерживается **SQLite, один процесс / один контейнер / один uvicorn worker**. PostgreSQL и несколько реплик не поддерживаются. Автоматические миграции добавляют поля, нормализуют домены и шифруют старые секреты; перед этим нужен бэкап. Коллизия нормализованных доменов останавливает обновление, а не объединяет сайты.
5. Настройте relay: direct MX по умолчанию выключен (`ALLOW_DIRECT_MX=false`). Приватные SMTP-адреса и нестандартные порты тоже запрещены по умолчанию; `SMTP_ALLOW_PRIVATE_TARGETS=true` допустим только для доверенных внутренних relay/локальных тестов.
6. Для каждого SMTP-пользователя задайте в панели разрешённые домены. Пустой список означает запрет отправки. Роль `admin` не даёт неограниченный SMTP relay.

## HTTPS / SMTP TLS

Порт **3005** задан в Settings, `python -m app`, Docker и установщике; WEB_PORT может переопределить его одновременно в launcher и Compose. Веб-порт Docker опубликован только на `127.0.0.1:3005`. Установите HTTPS reverse proxy на хосте (пример `deploy/Caddyfile.example`) и держите `COOKIE_SECURE=true`. Установщик не настраивает DNS/ACME/firewall самостоятельно. Флаг `--local-http` — только локальная разработка; он не публикует панель наружу.

Submission-порт хоста — 587; внутренний порт сервиса — 2525. Поместите cert.pem/key.pem в `tls/`, дайте непривилегированному пользователю контейнера право чтения и задайте `TLS_CERT_PATH=/app/tls/cert.pem`, `TLS_KEY_PATH=/app/tls/key.pem`. AUTH недоступен до STARTTLS, в том числе если TLS отсутствует или cert/key не загружаются. Клиент должен проверять доверие, срок и имя сертификата; сервисная диагностика проверяет только загрузку цепочки и соответствие cert/key.

Не задавайте произвольные trusted proxy. Uvicorn должен доверять forwarded headers только своему reverse proxy; на уровне приложения `TRUSTED_PROXY_IPS` пуст по умолчанию. Launcher доверяет forwarded headers только localhost; если reverse proxy находится на Docker gateway, явно укажите его точный IP в TRUSTED_PROXY_IPS, иначе Origin/CSRF-проверки за HTTPS proxy не смогут корректно определить схему. Не используйте `*`. При запуске вне Docker явно ограничивайте bind/firewall: один только Compose не защищает другой способ запуска.

## Входящая почта

По умолчанию `INBOUND_ENABLED=false`: сервис не выдаёт себя за полноценный mailbox и отклоняет входящие письма. При включении принимает только локальные активные домены, сохраняет полный оригинальный MIME (base64 + шифрование) до `250`. При отказе БД возвращает `451`. Вложения сохраняются как часть MIME, но IMAP, просмотр/скачивание вложений, антивирус, mailbox API и политика удаления входящих MIME не реализованы. Не публикуйте MX, если входящие не включены; DNS-раздел пока содержит справочные MX-примеры.

## Контракты отправки

- Старые `POST /api/emails` и `/api/send` сохранены: синхронная попытка отправки, тот же HTTP-контракт успеха/ошибки. Для ошибок частичной многополучательной отправки повтор всего запроса всё ещё может создать дубликаты. Для этих старых endpoints idempotency не добавлен.
- `POST /api/outbox` — новый асинхронный endpoint, **ровно один получатель в задании**, ответ `202`. Тело: `from_email`, `to`, `subject`, `html`, `text`, как у `/api/emails`. Заголовок `Idempotency-Key` необязателен; рекомендуется всегда. Глобальный ключ должен задать `?site_domain=example.com`.
- Повтор ключа с тем же содержимым возвращает прежнее задание, с другим — `409`. Ключ scoped к сайту. Записи завершаются и удаляются после `OUTBOX_RETENTION_DAYS` (7 дней): окно idempotency ограничено этим сроком.
- `GET /api/outbox/{id}` — статус; ключ другого сайта получает `404`.
- SMTP AUTH теперь подтверждает **сохранение в очереди**, а не факт доставки (`250 Message durably queued`). Оригинальный MIME сохраняется при отправке, маршруты совпадают с REST.
- Статусы: `queued`, `sending`, `accepted`, `failed`, `unknown`; `received` для входящих. `accepted` — удалённый SMTP relay принял письмо, не доказательство доставки в ящик. Старое имя webhook-события `email.sent` сохранено для совместимости; payload status теперь `accepted`.
- Отказ соединения повторяется с backoff. Обрыв/timeout после начала SMTP send считается `unknown`, следующие relay и автоповторы не запускаются. Незавершённые `sending` после перезапуска переходят в `unknown`: проверьте журналы провайдера перед ручной отправкой. После подтверждённого SMTP DATA 5xx повтор не выполняется. Exactly-once в SMTP не гарантируется.
- Исходящие MIME/тела очереди содержат персональные данные и шифруются, но ключ на том же диске без внешнего secret-store не защищает от полной компрометации сервера. Укажите `DATA_ENCRYPTION_KEYS` для внешнего управления ключом.

Пример:

```bash
curl https://admin.example.com/api/outbox \
  -H 'Authorization: Bearer sm_ваш_ключ' \
  -H 'Idempotency-Key: order-123-receipt' \
  -H 'Content-Type: application/json' \
  -d '{"from_email":"hello@example.com","to":"user@example.net","subject":"Receipt","text":"Thank you"}'
```

## Секреты / ротация

Relay password, provider password, DKIM private key, raw inbound MIME и payload очереди шифруются Fernet. `DATA_ENCRYPTION_KEYS` — ключи через запятую, первым новый, далее старые. Остановите процесс, сделайте бэкап, задайте новый ключ + старые, запустите: миграция перешифрует данные первым ключом. Проверьте отправку и backup/restore, только затем убирайте старый ключ. Старые резервные копии требуют соответствующих старых ключей. Не меняйте ключ без процедуры ротации.

Пустой пароль в HTML-форме сохраняет прежний; явный checkbox удаляет. В API провайдеров пропущенный password сохраняет прежний, пустая строка очищает (см. код/тесты). Пароли relay никогда не подставляются в HTML; API provider использует `has_password`.

## SSRF / webhooks

HTTPS включён по умолчанию. URL проверяется при сохранении и перед отправкой; TCP подключение pinning к публичному IP защищает от повторного DNS-резолвинга на private target. TLS использует оригинальный hostname. HTTP redirects не выполняются; environment proxies отключены. Есть небольшой покрытый тестами hook HTTPX/HTTPcore (версии ограничены в pyproject). Для больших обновлений этих библиотек повторите regression-тесты. Egress firewall всё равно рекомендуется.

SMTP подключение также pinning к проверенным IP с сохранением SNI/проверки hostname. По умолчанию разрешены только 25/465/587/2525 и публичные адреса. Секретные credentials не отправляются без TLS. Параметры private-targets в тестах включены **явно**, а не ослаблены в production defaults.

## Backup / restore

```bash
python tools/backup.py backup data/smtp.db backups/smtp.db
# STOP service. Move current DB aside manually; tool refuses overwrite.
python tools/backup.py restore backups/smtp.db data/smtp.db
```

Скрипт использует SQLite online backup API, `integrity_check`, права 0600 и не перезаписывает существующий файл. В Docker сначала получите доступ к именованному volume либо выполняйте инструмент внутри контейнера (tools нужно скопировать/смонтировать); пути `data/` на хосте и в named volume — разные места. После restore восстановите тот же ключ шифрования и протестируйте чтение секретов/отправку. Автоматическая отправка по реальным адресам при проверке восстановления не выполнялась.

## Что ещё не готово

- Несколько процессов/реплик, PostgreSQL/Alembic, распределённые лимиты, дневные per-site quotas и bounce/DSN suppression.
- SMTP AUTH bcrypt/DB callback остаётся синхронной короткой операцией в listener thread; сама доставка вынесена в отдельный async worker/to_thread. Это не обещание высокой нагрузки.
- У старых sync endpoints нет долговечного outbox до сетевого вызова; используйте новый `/api/outbox` для надёжной асинхронной отправки.
- Нет полного UI для входящих вложений, template preview/test-send, периода/provider/site-фильтров общего журнала и ручного управления `unknown`; очередь имеет фильтр по статусу и пагинацию.
- Health API сохраняет прежний лёгкий контракт; подробная защищённая диагностика доступна в `/admin/settings`, но не является полноценным мониторингом задержки очереди/доставляемости.
- Desktop/mobile QA выполнена на изолированной тестовой БД: 1440 и 390 px, формы, меню, ошибка входа и пустая очередь. Широкие таблицы и код прокручиваются внутри блока. См. reports/VISUAL_QA.md.
- Реальные DNS, доверие production-сертификатам, HTTPS proxy, Docker deployment, firewall и доставляемость у внешних SMTP-провайдеров требуют отдельной проверки на сервере. Production-деплой не выполнялся.
